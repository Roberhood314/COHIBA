# Review one boundary: SI authority → PostgreSQL commit

**Status: seeking independent review; no independent audit completed by this kit.**

Target: [`916f9f6f8d0403a32fbfe83f0f565871ec7e051c`](https://github.com/Roberhood314/COHIBA/tree/916f9f6f8d0403a32fbfe83f0f565871ec7e051c). The kit may change; the target does not. Findings must identify the target SHA. A later fix needs a separate retest SHA.

## Start in one command

Prerequisites: Git, Node **24.15+ below 25**, npm and network access to GitHub/npm. From a checkout containing this kit:

```sh
npm run review:si
```

No initial `npm install` is needed. The runner fetches the exact target into a temporary checkout, installs its locked dependencies with lifecycle scripts disabled, runs two synthetic test suites, saves logs plus source SHA-256 hashes under `operations/evidence/independent-review/`, then removes the temporary checkout. Use `-- --output=/absolute/new-directory` for another report location; existing directories are rejected. The runner does not inherit database, wallet or service environment variables. It is **not an OS sandbox**: inspect the code before running it. Git/npm can use normal local network configuration.

The default backend is embedded PGlite with a serialized adapter. It checks local behavior but cannot establish native multi-client PostgreSQL locking behavior. The `SI Pinned Review` workflow separately runs the same pinned tests against a fresh PostgreSQL 18 service and uploads both evidence sets. Download the workflow artifacts and compare SHA, backend, logs and source hashes. CI evidence is generated by the project, not by an independent reviewer.

## Three falsifiable questions

1. **Revocation:** after `gate.revoke()` acknowledges a local principal/binding/delegation revocation, can a fresh action still commit using an otherwise valid signed status? A commit already admitted before revocation obtains the lock may finish before revocation acknowledges; that is the documented ordering, not a bypass.
2. **Substitution:** can a valid agent signature commit a different resource, action, audience or payload than the authorized scope and exact expected request? Distinguish malicious agents from a compromised service that supplies dishonest expectations.
3. **Replay/rollback:** can concurrent reuse produce more than one durable business effect, or can a failed/expired transaction leave a consumed nonce or an effect? Reproduce concurrency on native PostgreSQL, not only the serialized embedded adapter.

Useful additional checks: credential-epoch rollback, approval nonce reuse, durable revocation after adapter restart and expiry at deferred COMMIT.

## Scope and trust assumptions

Read the files in [manifest.json](manifest.json), especially the verifier, PostgreSQL adapter, fixture and tests. Trace `commitAuthority` to `createPostgresCommitGate` and the test `onCommit` write. Review includes the signed one-level authority chain and atomic SQL admission/effect behavior. Test helpers and dependency lockfile are included for reproduction, not a claim that every dependency has been audited.

The service pins trusted issuer keys and supplies honest expected request values. A principal's authorized signing key, issuer status and server/DB administration are trusted. All participating service instances use the same durable database. The business callback writes **through the provided transaction connection**, performs no irreversible external effect, and propagates failure. PostgreSQL and clocks operate within the documented deployment assumptions. A malicious service/DB administrator is outside this boundary.

Excluded claims: global revocation across separate databases, Byzantine consensus, full endpoint mediation, arbitrary HTTP/on-chain effect atomicity, payment settlement, personhood verification, production key custody, and blanket quantum resistance. Pi/Open USD checkout and HS2 are separate surfaces. This review does not authorize production attacks or mainnet operations.

## Submit a finding

For safe, non-sensitive findings, open the **SI Boundary Review** issue form. Include a minimal local reproduction or test patch, exact target SHA, expected/actual durable DB state, backend and preconditions. A failing test without an impact explanation is useful evidence, not automatically a vulnerability.

Sensitive findings follow [SECURITY.md](../../SECURITY.md). Private intake is not assumed active: use only a minimal non-sensitive intake until the maintainer establishes a private channel. Do not place exploit details in public issues, artifacts or PRs.

See [handling and recognition](HANDLING.md), [finding template](FINDING.md), [review record](REVIEW_RECORD.md), and [outreach drafts](OUTREACH.md). Participation can be one question or one test; a whole-system audit is not required.
